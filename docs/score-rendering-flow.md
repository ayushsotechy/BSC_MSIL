# Score Sheet Rendering And Power Apps Migration Notes

This document explains how Admin, MSIL, and Dealer users see BSC score summaries and full score sheets in the current vanilla frontend. It also explains how MongoDB `_id`, dealer code, frontend state, and `bscExcelParser.js` fit together.

## Core Rendering Model

The backend does not send HTML for tables. It sends JSON.

The frontend works like this:

```text
Static HTML page loads
 -> page CSS applies layout and visual styling
 -> page JS fetches JSON from backend
 -> JS creates table rows/cells using DOM manipulation
 -> JS injects rows into existing HTML containers
```

So the app is already split into:

```text
HTML = page shell and placeholders
CSS = visual styling
JS = data fetching, state, DOM rendering
Backend = JSON data and persistence
```

Current frontend folders:

## Backend Score Data Shape

`backend/utils/bscExcelParser.js` does not render HTML. Its job is to create the JSON structure that the frontend later renders.

During Excel upload, the parser creates score data shaped like this:

```js
{
  _id: "...",
  dealerCode: "EAST 3MTLAZ",
  dealerName: "MITTAL AUTOZONE",
  region: "EAST 3",
  month: "August",
  fiscalYear: "2027",
  businessAreas: [
    {
      areaName: "Sales Performance",
      parameters: [
        {
          sNo: 1,
          parameter: "All Models Wholesales Performance",
          earlyBird: {
            maxPoints: 40,
            minPoints: 0,
            achieved: 40
          },
          fullYear: {
            maxPoints: 40,
            minPoints: 0,
            achieved: 40
          }
        }
      ]
    }
  ]
}
```

The important rendering contract is:

```text
score.businessAreas[].areaName
score.businessAreas[].parameters[].sNo
score.businessAreas[].parameters[].parameter
score.businessAreas[].parameters[].earlyBird
score.businessAreas[].parameters[].fullYear
```

The frontend score table renderers depend on this shape.

## Where `_id` Comes From

`_id` is not created by `bscExcelParser.js`.

The parser creates the score object. When the score object is inserted/upserted into MongoDB through Mongoose, MongoDB automatically assigns `_id`.

Bulk save flow:

```text
frontend previewed scores
 -> POST /api/bsc/bulk-save
 -> bsc.controller.js bulkSaveBscScores()
 -> BscScore.bulkWrite(...)
 -> MongoDB creates _id for new score documents
```

Each saved score document contains both:

```text
_id = exact MongoDB score sheet document id
dealerCode = dealer identity/code
```

They are not the same thing.

A dealer can have multiple score sheets across month/fiscal year combinations, so `_id` is used to open one exact score sheet.

## Admin Summary Table Flow

Admin page:

```text
frontend/public/vanilla/admin/index.html
frontend/public/vanilla/admin/styles.css
frontend/public/vanilla/admin/script.js
```

The summary table shell is already in `admin/index.html`:

```html
<table id="bsc-table" class="dashboard-table" hidden>
  ...
  <tbody id="bsc-table-body"></tbody>
</table>
```

The table headers are present in HTML. The row data is generated by `admin/script.js`.

Flow:

```text
Admin page loads
 -> admin/script.js calls GET /api/bsc/score?summary=true
 -> backend returns summary score rows
 -> state.rows stores those rows in browser memory
 -> renderRows() loops over state.rows
 -> JS creates <tr> and <td> elements
 -> JS appends rows into #bsc-table-body
```

The summary response includes `_id`, but `_id` is not shown as a visible column. It remains inside the JavaScript row object.

Admin row actions:

```text
View -> ../score/?id=<row._id>&mode=view
Edit -> ../score/?id=<row._id>&mode=edit
```

So Admin does not render the full score sheet inside the Admin page. Admin transfers the detailed rendering work to the shared `score` page.

## MSIL Summary Table Flow

MSIL page:

```text
frontend/public/vanilla/msil/index.html
frontend/public/vanilla/msil/styles.css
frontend/public/vanilla/msil/script.js
```

The MSIL summary table shell is already in `msil/index.html`:

```html
<table id="bsc-table" class="dashboard-table" hidden>
  ...
  <tbody id="bsc-table-body"></tbody>
</table>
```

Flow:

```text
MSIL page loads
 -> msil/script.js calls GET /api/bsc/score?summary=true
 -> msil/script.js calls GET /api/access-control
 -> JS finds dealers assigned to the logged-in MSIL person
 -> JS filters score summaries to assigned dealer codes
 -> state.rows stores allowed rows in browser memory
 -> renderRows() creates <tr>/<td> rows
 -> JS appends rows into #bsc-table-body
```

MSIL has only a View action:

```text
View -> ../score/?id=<row._id>&mode=view
```

Like Admin, MSIL does not render the full detailed score sheet inside the MSIL dashboard. It opens the shared `score` page.

## Shared Score Page For Admin And MSIL

Shared score page:

```text
frontend/public/vanilla/score/index.html
frontend/public/vanilla/score/styles.css
frontend/public/vanilla/score/script.js
```

This page is used by:

```text
Admin View
Admin Edit
MSIL View
```

The full score table is not hardcoded in `score/index.html`. The HTML only contains an empty container:

```html
<section id="score-content" class="score-content" hidden></section>
```

Flow:

```text
Browser opens /vanilla/score/?id=<scoreMongoId>&mode=view
 -> score/script.js reads id from URL
 -> score/script.js calls GET /api/bsc/score/:id
 -> backend returns full score JSON
 -> renderScore(score) runs
 -> renderTopFields()
 -> renderInfoTable()
 -> renderScoreTable()
 -> renderNote()
```

The detailed table is created with DOM manipulation:

```js
const table = document.createElement('table');
const thead = document.createElement('thead');
const tbody = document.createElement('tbody');
```

Then JS loops over:

```js
score.businessAreas
area.parameters
```

This creates:

```text
Business area rows
Parameter rows
Subtotal rows
Grand total row
```

Example visual result:

```text
Sales Performance
  1 All Models Wholesales Performance
  2 ARENA SUV Models Wholesales Performance
  ...
Sales Performance Total
```

The table structure and row generation are in `score/script.js`. The styling is in `score/styles.css`.

## Dealer Login And Score Fetch Flow

Dealer login starts in:

```text
frontend/public/vanilla/auth/script.js
```

Dealer submits username/password with role `dealer`.

Frontend calls:

```text
POST /api/access-control/login
```

Backend controller:

```text
backend/controllers/accessControl.controller.js
```

For dealer role, the backend searches `DealerAccessCredential` by:

```text
dealerCode
or
mailId
```

If valid, backend returns a user object containing:

```js
{
  role: "dealer",
  dealerName: "...",
  dealerCode: "..."
}
```

The frontend stores it in browser localStorage:

```js
localStorage.setItem('bsc_user', JSON.stringify(user));
```

Then the user is redirected to:

```text
/vanilla/dealer/
```

## Dealer Score Sheet Flow

Dealer page:

```text
frontend/public/vanilla/dealer/index.html
frontend/public/vanilla/dealer/styles.css
frontend/public/vanilla/dealer/script.js
```

Dealer does not use the shared `score` page.

Dealer has its own score content container:

```html
<section id="score-content" class="score-content" hidden></section>
```

Dealer JS reads the logged-in user from localStorage and gets:

```js
currentUser.dealerCode
```

Then it fetches:

```text
GET /api/bsc/score?dealerCode=<dealerCode>
```

Optional filters can add:

```text
month
fiscalYear
```

Flow:

```text
Dealer page loads
 -> dealer/script.js reads bsc_user from localStorage
 -> gets dealerCode
 -> calls GET /api/bsc/score?dealerCode=<dealerCode>
 -> backend returns matching BscScore rows
 -> dealer/script.js picks current score
 -> renderScore(currentScore)
 -> renderTopFields()
 -> renderInfoTable()
 -> renderScoreTable()
```

Dealer has its own duplicated score table renderer inside `dealer/script.js`. It does not call or import `score/script.js`.

This means:

```text
Admin/MSIL detailed score sheet = shared score folder
Dealer detailed score sheet = dealer folder itself
```

## Browser Memory State

Admin and MSIL summary rows are stored in normal browser runtime memory.

For Admin:

```js
state.rows = scoreResponse.data
```

For MSIL:

```js
state.rows = filteredAssignedScores
```

This is not MongoDB, not localStorage, and not a file. It is temporary JavaScript memory while the page is open.

If the page refreshes, the data is fetched again.

Keeping 377 summary rows in browser memory is fine because:

```text
GET /api/bsc/score?summary=true
```

excludes the heavy `businessAreas` field. Only lightweight summary data is kept for dashboard tables.

The full detailed score sheet is fetched only when View/Edit is clicked.

## Important Clarification About Backend HTML

No backend HTML is fetched for these tables.

The backend only returns JSON. All table rendering is frontend-side.

Admin/MSIL do not fetch the score page HTML using JS. They navigate the browser to the shared score page URL:

```text
/vanilla/score/?id=<scoreId>&mode=view
```

Then `score/index.html`, `score/styles.css`, and `score/script.js` handle the detailed rendering.

## Power Apps / Power Automate Migration Mapping

The current structure maps well to Power Apps because the app already uses:

```text
Summary screen
 -> selected score id
 -> detail screen
 -> nested score data rendering
```

Power Apps equivalent:

```text
Admin dashboard gallery/table
 -> load score summaries from Dataverse or Power Automate
 -> keep ScoreId hidden
 -> View/Edit sets selected ScoreId
 -> navigate to detail screen
 -> detail screen fetches full score JSON
 -> render businessAreas and parameters
```

MSIL equivalent:

```text
MSIL dashboard gallery/table
 -> load score summaries
 -> load access-control assignments
 -> filter assigned dealers
 -> keep ScoreId hidden
 -> View sets selected ScoreId
 -> navigate to detail screen
```

Dealer equivalent:

```text
Dealer screen
 -> identify logged-in dealerCode
 -> fetch score by dealerCode
 -> render same score data shape
```

## Recommended Dataverse Shape

The clean long-term Dataverse model is normalized:

```text
BscScores
  ScoreId
  DealerCode
  DealerName
  Region
  Month
  FiscalYear
  CurrentYearBand
  YearScore

BscBusinessAreas
  BusinessAreaId
  ScoreId lookup
  AreaName
  SortOrder

BscParameters
  ParameterId
  BusinessAreaId lookup
  ScoreId lookup
  SNo
  ParameterName
  EarlyMaxPoints
  EarlyMinPoints
  EarlyAchieved
  FullMaxPoints
  FullMinPoints
  FullAchieved
```

Power Automate can then return the same nested JSON shape the current JS expects.

Alternative simple model:

```text
BscScores
  ScoreId
  DealerCode
  Month
  FiscalYear
  ScoreJson
```

This is easier for reusing current JS but weaker for Dataverse filtering and reporting.

## Migration-Friendly Summary

The most important thing to preserve is the data contract:

```js
{
  scoreId: "...",
  dealerCode: "...",
  dealerName: "...",
  month: "...",
  fiscalYear: "...",
  businessAreas: [
    {
      areaName: "...",
      parameters: [
        {
          sNo: 1,
          parameter: "...",
          earlyBird: { maxPoints, minPoints, achieved },
          fullYear: { maxPoints, minPoints, achieved }
        }
      ]
    }
  ]
}
```

If Power Automate can return this shape from Dataverse, the current HTML/CSS/JS rendering approach can be adapted cleanly.

## One-Line Summary

Admin and MSIL render summary rows in their own scripts, then navigate to the shared score page for details; Dealer renders the detailed score sheet inside its own page; `bscExcelParser.js` creates the nested score JSON shape that all these renderers depend on.
